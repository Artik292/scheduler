# Приватные данные преподавателей и история Git

Реальные списки преподавателей и SQL-дампы сняты с отслеживания Git, но сохранены локально. Правила `.gitignore` защищают `docs/*.sql`, `docs/*.xlsx`, `docs/*.xls`, `docs/*.csv`, `database/imports/*.csv`. В документации и тестах реальные имена удалены. В `database/fixtures/teacher_roster.csv` находятся только вымышленные записи.

Рабочая база не очищается и не переимпортируется этим выпуском. Реальный CSV исключён из Docker-образа; локальный Compose подключает его каталог только для чтения. Для уже выполненной миграции `007` CSV больше не нужен. Для первого облачного импорта используйте закрытый Actions secret `TEACHER_ROSTER_CSV`, описанный в [инструкции импорта](TEACHER-ROSTER.md).

## Что уже подготовлено

`bin/prepare_history_cleanup.py` создаёт отдельный bare mirror, резервную копию исходной истории и отчёт проверки. Скрипт удаляет приватные экспорты из всех доступных коммитов, заменяет известные имена в файлах проекта и сообщениях коммитов, проверяет результат. Он сохраняет сторонний `vendor/` и авторов коммитов. Базы данных скрипт не касается.

Рабочие ветки, stash и история исходной папки не переписываются. В копии исключаются служебные tree-снимки редактора; ветки и stash проходят фильтрацию. Файлы внутри `var/history-cleanup-*` приватные и игнорируются Git. В том числе bundle содержит исходную историю: храните его локально.

Подготовленная до коммита копия — предварительная проверка. Её `publish-reviewed-history.sh` откажется запускаться. Чтобы включить новые изменения, сначала создайте свой коммит и затем повторите подготовку.

## 1. Сохранить изменения локальным коммитом

Выполняйте из корня проекта. Для текущего выпуска нужен локальный `main` со всеми проверенными изменениями. Сначала проверьте ветку и diff:

```bash
git branch --show-current
git status --short
git diff
git diff --cached --stat
```

Удаления пяти приватных файлов уже подготовлены через `git rm --cached`: файлы остались на диске. Остальные изменения добавьте и закоммитьте самостоятельно. Например, после проверки полного списка изменений:

```bash
git add -A
git diff --cached --stat
git commit -m "Improve mobile layout and keep teacher data outside Git"
```

На этом этапе не отправляйте обычный push: он ещё будет содержать старую историю. Если вы работаете в другой ветке, сначала включите её проверенный коммит в локальный `main`.

## 2. Подготовить свежую очищенную историю

Уже установлено отдельное временное окружение `/tmp/scheduler-history-tools`. Пока оно существует:

```bash
python3 bin/prepare_history_cleanup.py \
  --filter-repo /tmp/scheduler-history-tools/bin/git-filter-repo
```

Если временного окружения больше нет, создайте его заново:

```bash
python3 -m venv /tmp/scheduler-history-tools
/tmp/scheduler-history-tools/bin/python -m pip install git-filter-repo==2.47.0
python3 bin/prepare_history_cleanup.py \
  --filter-repo /tmp/scheduler-history-tools/bin/git-filter-repo
```

Скрипт выводит каталог `var/history-cleanup-...`, путь к `report.json` и к резервной копии `before-cleanup.bundle`. В отчёте должны быть:

- `source_has_uncommitted_changes: false`;
- `remaining_known_names_or_private_exports: 0`.

Если в GCP ещё не применена `007`, подготовьте секрет CSV до первого релиза. Приватные локальные CSV и старые SQL-экспорты должны оставаться на месте до подготовки очистки: по ним скрипт получает имена для поиска во всей истории.

## 3. Проверить и вручную опубликовать

На время публикации договоритесь не обновлять ветки и временно отключите GitHub Actions в **Settings → Actions → General → Actions permissions**. Очистка затрагивает старые ветки с прежними workflow; это предотвращает их случайный запуск при обновлении истории. Если защита веток запрещает force push, временно разрешите его для своей учётной записи.

Вместо `var/history-cleanup-НУЖНЫЙ-КАТАЛОГ` ниже подставьте каталог из последнего успешного запуска после коммита:

```bash
export SCHEDULER_CLEANUP_DIR="$PWD/var/history-cleanup-НУЖНЫЙ-КАТАЛОГ"
cat "$SCHEDULER_CLEANUP_DIR/report.json"
cat "$SCHEDULER_CLEANUP_DIR/publish-reviewed-history.sh"
git -C "$SCHEDULER_CLEANUP_DIR/clean.git" log --all --oneline -10
```

После проверки выполните **самостоятельно**:

```bash
bash "$SCHEDULER_CLEANUP_DIR/publish-reviewed-history.sh"
```

Этот файл делает один `git push --atomic` с явными ветками и `--force-with-lease` для каждой ветки/метки. Он не использует `push --mirror` и не отправляет служебные refs редактора, stash или upstream. Проверка lease отклонит публикацию, если удалённая ветка изменилась после локального снимка. В этом случае получите свежие refs (`git fetch origin`), включите новые коммиты и заново подготовьте очистку. Не заменяйте lease на безусловный `--force`.

Скрипт рассчитан на уже полученные локально refs `origin`: перед окончательной подготовкой выполните `git fetch origin`, если после последнего fetch кто-то обновлял репозиторий. Если появились новые удалённые ветки, их тоже нужно сначала получить.

## 4. Возобновить обычную работу

Включите Actions и прежнюю защиту веток. Запустите **Actions → Build, verify and deploy → Run workflow → main** — это проверит и выпустит новый интерфейс.

После переписывания истории используйте новый clone репозитория. Сохраните `.env` и приватные файлы отдельно; MySQL volume и облачная БД не зависят от Git. Другим разработчикам также нужен новый clone: push из старой копии способен вернуть удалённую историю.

Обновление веток GitHub не удаляет копии в чужих форках, локальных клонах и кэшах старых PR. Для недоступности старых ссылок обратитесь в GitHub Support, указав первые изменённые коммиты из `clean.git/filter-repo/first-changed-commits`. Подробности и ограничения: [официальная инструкция GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).
